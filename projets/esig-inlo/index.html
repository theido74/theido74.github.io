INLO

Une plateforme pour apprendre Python, écrite en Rust. L'idée : un tuteur qui pose des questions au lieu de donner les réponses, et un code d'apprenant toujours exécuté dans une boîte fermée.

Où en est le projet. Le dépôt est jeune (créé le 12 novembre 2026). Il contient un socle (quatre modules Rust, une API qui répond à un test de santé, une migration, un exercice), des décisions d'architecture et un plan sur sept sprints. Une grande partie de ce qui est décrit ici reste à construire, et les pages le disent.

Dépôt privé de l'ESIG (Genève) : le code n'est pas public, donc pas de lien vers lui.

Que devient un code soumis ?

En attente d'une soumission.

    Limites par défaut lues dans le code du module d'exécution : 5 secondes, 128 Mo de mémoire, 64 Kio de sortie. Le temps de la simulation est accéléré. Ce que fait vraiment le dépôt aujourd'hui : un module « bac à sable » qui définit ces limites et ses erreurs, sans encore de conteneur derrière.

    Quatre modules, des frontières nettes

    Le projet est découpé en modules Rust (des « crates »), avec une règle par module. Choisissez-en un.

    Le trait en pointillé signale un point que le plan de refonte veut corriger : l'API ne devrait jamais pouvoir exécuter de code. Le plan prévoit aussi de découper davantage (worker, tuteur, stockage…).

    Ce que la plateforme vise

    Comment c'est construit

    • Rust (édition 2024) en espace de travail à plusieurs modules, avec Clippy en mode pédantique et unsafe interdit.
    • API avec Axum et PostgreSQL (sqlx) ; interface avec Leptos, compilée en WebAssembly.
    • Exercices en Python, chacun avec énoncé, code de départ, solution et tests pytest ; la solution doit passer ses propres tests.
    • Intégration continue : formatage, lints et tests Rust, tests des exercices, construction de l'image du bac à sable et tests d'évasion.
    • Méthode d'équipe : une branche par tâche, jamais de commit direct sur la branche principale, messages en « Conventional Commits », relecture par au moins une autre personne.

    Sécurité : le code d'un apprenant est hostile par défaut

    Règle de la conception : aucun accès au réseau, système de fichiers en lecture seule, utilisateur sans droits, limites de temps, de mémoire et de sortie. Rien n'est jamais exécuté hors du bac à sable, tests compris.

    C'est l'intention documentée du projet ; la mise en œuvre complète est dans les tickets à faire.
